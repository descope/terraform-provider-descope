# Adding a Resource

How to add a new standalone resource. For the model itself (attributes, struct, `Values()` and `SetValues()`), read
`internal/models/CLAUDE.md` first.

## The endpoint decides the constructor

Pick the constructor by the shape of the backend API, not by what the feature is:

- **Entity with a server-assigned id** on one route (`POST` create, `GET ?id=`, `PUT` update, `DELETE ?id=`): use
  `newResource` with operations written longhand in the resource's file. `NewAppPermissionResource` in `apps.go` is
  the reference: Create reads the new id from the returned entity, Update puts the id in the body, and reads and
  deletes pass it as a query parameter.
- **Entity scoped under a parent** (an application, an auth method): set `ScopedRead` and `ScopedDelete` instead of
  `Read` and `Delete`. The model must have an `app_id` or `method` attribute, which `baseResource` uses for the scope.
- **Singleton settings** on one `GET`/`POST` settings route: use `newSettingsResource` with the path. It always
  exists, its id is the project id, and destroying it only removes it from state.
- **Connectors** are generated by terragen from the content repo templates, and registered in `connectors.go`.
- Never use `newInfraResource` for anything new: the `/v1/mgmt/infra` endpoint is frozen.

Don't build a shared helper for a new endpoint family. Operations stay as plain closures over `infra.Client` in the
resource's own file, so each endpoint's quirks are visible in one place. When the endpoint doesn't match the ideal
shape (an envelope around the entity, an id in the path, a delete through a `POST` body, a create that returns no
body), the adapter goes in those closures, as in `lists.go` and `authorization.go`, and the fix belongs in the
backend.

## Steps

1. **Model.** Create `internal/models/<package>/` with the schema and model. Resource models implement
   `helpers.ResourceModel`: `id` is `stringattr.Identifier()`, `project_id` is
   `stringattr.Required(stringplanmodifier.RequiresReplace())`, and `GetID`, `SetID` and `GetProjectID` return them.
   The schema's `MarkdownDescription` is the resource's description in the registry docs.
2. **Resource.** Add the constructor to a file here, named after the resource.
3. **Registration.** Add the constructor to the resources list in `internal/provider/provider.go`.
4. **Deletion protection.** Only for entities whose deletion loses something that can't be recreated from the
   configuration, such as applications with issued credentials. Add a `deletion_protection` attribute using
   `boolattr.Tristate()` and implement `helpers.DeletionProtectionDefaulter`, following `inboundapp`.
5. **Documentation.** Run `make terragen` to create the placeholders in `docs/raw/<package>/`, replace every `//`
   placeholder with a description, then run `make terragen` and `make docs` again.
6. **Acceptance test.** Add a helper for the resource in `tools/testacc/resource.go`, then a test in the model's
   package using `testacc.Run`. Pack as many attributes into each step as possible, since every step is a full plan
   and apply. End with an import step that uses `testacc.GenerateImportStateID`.
7. **Sweeper.** If leaked test entities would pile up in the shared test project, add a target to `sweepTargets` in
   `tools/testacc/sweep_test.go`.
8. **tfexport.** A registered resource is picked up automatically, but it's only exported once discovery lists it.
   Read `tools/tfexport/CLAUDE.md`. `TestGenerativeCoverage` fails with a discovery gap until then, which is the
   intended guard.

## Import ids

`ImportState` parses the id by the resource's shape, and tfexport must emit the same formats:

- Singleton: `<project_id>`
- Entity: `<project_id>/<id>`
- Entity scoped by `method` or `app_id`: `<project_id>/<scope>/<id>`
- Company-level resource (no `project_id` attribute): `<id>`
